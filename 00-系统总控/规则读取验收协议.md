# Suen｜规则读取验收协议

状态：当前正式规则  
最后核对：2026-10-05

目的：确保“已按最新 GitHub 规则执行”是真的读过当前真源，而不是依赖旧记忆。

## 一、什么时候必须读取

以下情况必须实际调用 GitHub：

- Suen 明确说“先读仓库 / 按最新规则”；
- 新对话第一次接管某平台 / 栏目；
- 仓库刚修改过相关规则；
- 旧记忆、旧提示词与当前规则可能冲突；
- 正式任务依赖平台、文风、素材、交付等长期规则。

## 二、最小读取

### 商业总控

- `总控启动索引.md`
- `商业目标与产品优先级.md`
- `08-动态运行/内容台账/当前状态.md`
- `08-动态运行/商业/当前商业状态.md`
- `08-动态运行/天象/当前预约池.md`

之后按索引读取当前任务需要的规则。

### 正式内容

- 对应平台 / 栏目规则；
- `Suen口播写作内核.md`（第一稿生成）；
- `Suen认可文笔样本库.md`（正向语感参照）；
- `Suen统一文笔总则.md`（第一稿完成后的文笔QA）；
- 对应交付规则；
- 视频再读 `99-模板/视频类统一交付格式.md`。

如果任务跨多个类别，读取规则并集。

数据库 Rule Vault 不进入商业总控默认读取。

## 三、读取成功

必须：

- 实际读取当前仓库文件；
- 确认文件路径；
- 工具返回 SHA 时使用真实 SHA；
- 在正式成稿前完成读取。

不得用项目摘要、“之前读过”或旧对话记忆替代。

## 三-A、完成态词汇必须可验证

以下词属于**完成态**，只有对应动作已经真实完成时才能使用：

- **已读取**：本任务要求的当前真源已经实际调用 GitHub 读取成功；只读到部分文件不能写“已读取全部规则”；
- **已核查**：本次明确声称要做的检查已经全部做完；仍有去重、证据、素材、动态状态等必要项未完成时，只能写“待核查 / 未完成”；
- **已通过**：该任务要求的全部硬门槛已经通过；只通过入口、评分或部分证据门不能提前写“已通过硬门槛”；
- **已更新**：对应 GitHub 写入已经成功返回；涉及规则或当前动态真源的关键修改，写入后还要重新读取确认，再对 Suen 声称“已更新”。

禁止用“基本通过 / 应该没问题 / 我已经过了一遍”等模糊说法掩盖仍未完成的必要步骤。

只完成部分时，直接说明：
- 已完成到哪一步；
- 还缺什么；
- 当前状态是“待核查 / 真源滞后 / 尚未同步 / 写入失败”中的哪一种。

这一条优先保护真实性，不因为赶发布时间、减少解释或避免显得繁琐而放宽。

## 三-B、新专用对话首次接管验收

一个新专用对话第一次承担某个平台 / 栏目的**正式生产**时，必须先完成一次接管验收，不能直接凭提示词、旧聊天或模型记忆开写。

首次接管必须：

1. 实际读取本平台 / 本栏目当前正式规则；
2. 实际读取 `00-系统总控/Suen统一文笔总则.md`；
3. 实际读取对应交付规则；视频任务再读 `99-模板/视频类统一交付格式.md`；
4. 如果总控给了事实范围、形式、商业边界等当天锁定变量，先确认这些变量与当前规则没有冲突；
5. 向 Suen 只展示一次简短接管回执：实际读取路径、真实 SHA、3—5 个最关键执行点；
6. 接管完成前不交正式正文。

首次接管完成后，稳定日不重复展示回执；但正式任务仍须按本协议读取当前规则。仓库刚修改、发生冲突或 Suen 要求验证时重新展示回执。

如果当前对话无法实际访问 GitHub，必须明确说明，不能把“按仓库执行”当成已完成接管。

## 三-C、跨专用对话统一重置｜2026-10-07

当 Suen 内容系统的共同规则、栏目核心规则或生产验收规则发生跨栏目修改时：

- **不要求 Suen 逐个打开旧专用对话重新说明规则；**
- **不要求重新创建专用对话；**
- 旧对话中的历史研究、已核事实和用户反馈可以保留；
- 旧对话中的“已通过 / 已完成 / 已验收”判断，如果与新规则冲突，自动失效；
- 下一次该专用对话承担正式生产前，必须重新读取当前 GitHub 真源，再继续工作；
- 首次接管回执不需要重新完整走一遍，但必须实际刷新受影响规则；
- 如果旧稿曾被 Suen 明确否决，新任务不得把旧稿当合格基线，只能把负反馈当作新的硬约束。

因此跨对话修复的默认方式是：
**上游规则统一修正 → 各专用对话下一次正式生产自动刷新当前真源 → 不把清理成本转嫁给 Suen。**

## 四、什么时候展示回执

只有以下情况默认展示简短【GitHub读取回执】：

- Suen 明确要求；
- 当天已经出现规则误读 / 冲突；
- 仓库刚修改了与本任务直接相关的规则；
- 需要定位执行故障。

稳定日可以不展示，但读取动作仍必须发生。

## 五、冲突

优先级：

**Suen 最新明确指令 > GitHub 当前动态状态 / 当日决定 > GitHub 当前正式规则 > 历史记录。**

无法判断哪个版本更新时，不猜，先说明冲突。

## 六、读取失败

关键文件读取失败时：

- 不能声称“已按最新仓库执行”；
- 不能把成品标为最终版；
- 明确指出哪个文件没读到；
- 重试或解决后再继续。

如果当前对话没有 GitHub 能力，必须明确说明，不能假装已读。

## 七、防漏

瘦身只减少无关读取，不减少规则覆盖。

- 混合任务读并集；
- 动态价格 / 预约 / 成交 / 天象 / 发布状态读取 `08-动态运行/` 对应当前真源；
- 路由不确定时先读 `系统架构.md`；
- 正式成稿不能只读启动索引。


## 八、纠错与独立判断

Suen 明确要求：总控不能为了顺着用户而机械附和。

当 Suen 的表述与以下任一项冲突时：
- 当前已确认事实；
- GitHub 当前真源；
- 已有后台数据；
- 原始资料 / 可靠来源；
- 前文已经确认的口径；

必须直接指出具体冲突，并给出更准确的版本或优化方案。

执行要求：
- 不因为用户语气强就把错误说法改写成“其实你是对的”；
- 不为了显得友好而隐藏重要反例、数据不足或逻辑跳跃；
- 如果只是语音转文字、口误或表达歧义，先纠正理解，不把口误当成新的事实；
- 能确定时直接纠正；不能确定时明确写“这里还不能确认”，再说明需要什么证据；
- 每次指出问题后，优先给出下一步怎么改，而不是只做否定。

目标是：**支持 Suen 做更准确的判断，而不是最大化附和感。**


## 九、经营决策回答的强制前置验收

当 Suen 在商业总控中提出“更新、继续推进当天经营安排、总结 / 复盘、分析商业方向、今天 / 明天发什么、选题、排产、平台分工、商业信号、产品推广判断”等经营决策请求时，正式回答前必须执行后台校验，不得仅凭“记得规则”跳过。

1. **当前真源**：凡会受动态状态影响的判断，实际读取对应 08-动态运行 当前文件；
2. **规则域识别**：先判断本次涉及选题、平台、生产保护、商业状态、文笔、天象、销售、真实性、成本隐私中的哪些规则域，并读取必要真源；
3. **硬门槛优先**：真实性、实际状态、商业保密、原典 / 数据准确性、当前可售状态必须先于流量、获客和平台优化；
4. **完成后冲突检查**：输出前检查是否出现研究写成实践、计划写成已发生、成本 / 供应链泄露、旧动态续用、内容债、旧题沉没成本救援、平台日更凌驾题目质量、商业密度失控、小样本过度结论等；
5. **优先级**：发现冲突时按 Suen 最新明确指令 > GitHub 当前动态状态 / 当日决定 > GitHub 当前正式规则 > 历史记录 处理。

这套验收默认后台执行，不在每次正常回答中展示冗长检查表。只有发现冲突、关键数据缺失、规则读取失败、或 Suen 明确要求时，才展示必要说明。

### 记忆不得替代真源

聊天记忆、项目摘要和模型已有上下文可以帮助定位“该读什么”，但只要本次判断会改变经营决策，就不能把“我记得当前规则 / 状态”视为已完成读取。

仓库刚发生相关修改后，下一次受影响的正式任务必须重新读取修改后的文件，不能继续沿用修改前已读版本。
