# Suen System｜系统架构

状态：当前正式结构
最后核对：2026-09-18

## 0. 项目运营时区

本项目涉及内容发布日期、复盘日期、每日“总结 / 更新”日界线、Slack 运营记录时，默认使用：

**Asia/Shanghai（UTC+8）**

除非 Suen 当次明确指定其它地点 / 时区，不根据设备、VPN、系统推测位置自动改成日本、UTC 或其它时区。

因此：

- “今天 / 昨天 / 明天”默认按上海时间解释；
- 内容发布时间和复盘日期默认按上海日历日记录；
- 午夜附近如果工具返回其它时区，先换算到 Asia/Shanghai 再判断日期；
- 天象技术地点 / 时区仍由对应专用择时系统负责，不能用这个运营规则代替技术择时参数。

## 1. GitHub｜运营配置层

这个仓库的职责不是保存所有知识，而是让 **Slack + ChatGPT 的日常运营更稳定、更省事**。

负责：

- 商业总控规则；
- 总控 P0 / P1 / P2 优先级、生产保护与短交接；
- 商业信号、商业密度与动态状态有效期；
- 商业指标统计口径；
- 内容制作耗时、生产单元与投入产出判断；
- 内容主要验证假设、发布后结果回看与第一方信号升级；
- 每周商业复盘规则；
- 平台 / 栏目长期执行规则；
- Suen 跨平台共同文笔底线；
- 规则读取、执行验收与最终成稿 QA；
- Slack 频道分工与数据结构；
- 客户商业记录流程；
- 天象经营状态接口；
- 常用模板；
- 版本变更与废弃规则审计。

不负责：

- 完整课程规则；
- 数据库完整写入规范；
- 完整技术择时；
- 研究资料正文；
- 视觉资产与大文件；
- 独立项目自己的运营规则与自动化状态；
- 每天对标账号抓取到的动态样本。

## 2. Slack｜当天经营状态

当前核心频道：

- `#内容历史台账`：实际已发布内容与复盘事实；
- `#商业决策总控`：瓶颈、任务、商业信号、询盘、报价、成交、产品推进、主要验证假设与验证结果；
- `#天象检索与预约`：已经筛选过的天象经营状态。

Slack 保存动态状态；GitHub 保存 Slack / ChatGPT 怎么工作。

具体频道 ID、简称映射与改名规则见 `07-销售与Slack/Slack架构.md`。

## 4. ChatGPT｜协调执行层

处理任务时按问题类型选择真源：

- 问“今天发什么 / 推什么 / 卡在哪里” → Slack + GitHub；
- 问“今天哪些平台能卖 / 商业信号算不算重复 / 昨天的销售决定还能不能沿用” → `商业信号与动态状态规则.md` + Slack；
- 问“今天哪些任务必须先做 / 系统问题能不能打断生产” → `总控简化与生产保护规则.md`；
- 问“当前目标进度怎么算” → `商业指标口径.md` + Slack；
- 问“这类内容值不值得继续花这么多时间做 / 同一支跨平台怎么算生产成本” → `生产投入产出规则.md` + `#内容历史台账`；
- 问“这条内容到底验证了什么 / 什么时候能从单样本升级成重复信号” → `内容实验与验证规则.md` + `#商业决策总控` + `#内容历史台账`；
- 问“这周商业系统哪里卡住” → `每周商业复盘.md` + Slack；
- 问“栏目应该怎么写” → GitHub；
- 问“课程内部怎么教” → 课程专用系统 / Library；
- 问“数据库条目怎么写” → 数据库专用系统 / Obsidian；
- 问“这个时间能不能做” → 专用择时系统；
- 问具体原典 / 文物 / 研究材料 → Library / Drive / 外部研究来源；
- 问“对标账号最近在做什么” → 公开网络 / 平台近期真实内容 + `内容商业对标系统.md` 的双层方法。

### ChatGPT 启动读取规则

GitHub 已经是长期运营配置真源，因此不能只依赖旧对话记忆。

在以下情况，ChatGPT 应先刷新 GitHub 规则再执行：

1. **新对话 / 新会话第一次进入商业总控工作**；
2. Suen 明确说“仓库更新了 / 规则改了 / 看一下 GitHub”；
3. 当前任务与记忆中的规则存在冲突或不确定；
4. 第一次进入一个此前没有加载过的栏目 / 平台规则；
5. Suen 明确要求“先读仓库 / 按最新仓库执行”。

商业总控最小启动读取集：

- `README.md`
- `00-系统总控/系统架构.md`
- `00-系统总控/商业总控.md`
- `00-系统总控/总控简化与生产保护规则.md`
- `00-系统总控/每日总结与更新工作流.md`
- `00-系统总控/商业目标与产品优先级.md`
- `00-系统总控/商业信号与动态状态规则.md`
- `00-系统总控/商业指标口径.md`
- `00-系统总控/生产投入产出规则.md`
- `00-系统总控/内容实验与验证规则.md`
- `00-系统总控/内容商业对标系统.md`
- `00-系统总控/选题定稿硬门槛.md`
- `00-系统总控/Suen统一文笔总则.md`

如果是周复盘，再读取：

- `00-系统总控/每周商业复盘.md`

之后再按当天实际需要读取：

- 对应平台 / 栏目规则；
- 公众号专属规则；
- 销售 / 天象经营接口等。

**“读取 GitHub”必须是实际工具读取，不是口头声明。**

规则读取是否真的完成、什么时候必须显示文件路径 / SHA / 硬规则回执、读取失败后能不能继续生成，统一执行：

`00-系统总控/规则读取验收协议.md`

**每天“更新”仍必须重新读取三个 Slack 动态频道。**

GitHub 属于长期静态配置，不要求同一会话里每次“更新”都机械重读整个仓库；但只要仓库发生过修改、Suen 明确要求重新读取、规则存在疑问或当前成稿与规则可能冲突，就刷新相关文件。

### 对标的动态读取规则

对标体系分两层：

- 五个 benchmark 的长期方法存 GitHub；
- 近期具体创作属于动态公开信息，不固化在 GitHub。

每个 Asia/Shanghai 运营日第一次需要确定新的前台题目时：

- 根据当天 A / B / C / D 与瓶颈，实际查看最相关 2—3 个对标账号近期真实创作；
- 默认优先最近约 7—30 天；
- 同日已经刷新且任务没变时可以复用；
- 近期样本无法可靠取得时明确降级，不用长期印象冒充刚看过。

完整方法见 `内容商业对标系统.md` 与 `选题定稿硬门槛.md`。

### 阶段性规则的日期有效性

读取 GitHub 时，不能把带明确周期的阶段规则当永久规则。

例如：

- `商业目标与产品优先级.md` 的当前 30 天目标有结束日期；
- `03-公众号/阿赫特之门.md` 的冷启动阅读基线有 14 天测试周期和复核点。

如果当前日期已经超过规则中写明的周期 / 复核点：

- 先检查是否已有新的 Slack 正式记录或 GitHub 更新；
- 没有新版本时，把旧数字视为**上一阶段参考**，不要假装仍是当前正式 KPI / 最新基线；
- 不自行续期、外推或重新换算目标；
- 在下一次相关总控判断中明确提示需要复核 / 重算。

### 当日商业状态也有有效期

“今日纯内容 / 今日主推 / 今日明确不推 / 今日唯一商业信号 / 今日停更”等决定默认只对 Asia/Shanghai 当天有效。

跨日以后不得自动沿用昨天的日调度；是否继续必须读取当天最新 Slack 或 Suen 最新明确指令。具体执行见 `商业信号与动态状态规则.md`。

### 生成内容时

如果总控决定今天执行某个栏目：

- 总控只给当天任务、瓶颈、选题、商业边界和需要优化的运营变量；
- 专用栏目必须实际读取自己的长期规则；
- 共同文笔底线读取 `Suen统一文笔总则.md`；
- 正式成稿读取并执行 `文笔成稿验收协议.md`；
- 整个任务执行读取并执行 `专用对话执行验收协议.md`；
- 视频任务读取 `99-模板/视频类统一交付格式.md`；
- 当 Suen 明确要求仓库读取，或当天已经发生过规则误读 / 冲突，正式成稿前先输出【GitHub读取回执】；
- 不因为运营层改结构而覆盖栏目本来的事实核查、素材、文风和交付方式。

如果 GitHub 可访问但关键规则读取失败，不能继续把成品标成“最终版”；先解决读取失败。

如果规则已经正确读取，但任务在执行中出现返工、文笔漂移、素材转嫁或半成品停止，优先按 `专用对话执行验收协议.md` 排查执行故障，不先发明新的栏目理论或流程负担。

### 生产保护

一旦题目通过硬门槛，并已经确定栏目、题目、核心问题、A / B / C / D 与商业边界，同时新的正式前台内容已经按 `内容实验与验证规则.md` 写好发布前主要验证假设（稳定结构复用可写“无新增实验”），该任务进入生产保护状态。

P0 未完成以前：

- 不用非阻塞性的系统整理、README 美化、模板微调或附加任务中断主生产；
- 普通文笔、图片、链接、排版问题由执行对话自己修；
- 只有核心事实 / 证据、栏目路由、商业 / 天象硬边界或 Suen 最新明确指令发生真实变化时，才退回总控重新定题。

完整规则见 `总控简化与生产保护规则.md`。

### 专用对话拿不到当天总控时

如果某个栏目 / 平台专用对话无法可靠读取当天 `#商业决策总控` 或没有收到当天总控交接提示词：

- **不要假装已经读取总控；**
- 继续按该栏目自己的长期规则正常生成内容；
- 默认按**纯内容**执行；
- 不自行增加接单、报价、预约、购买、私信引导或其它商业 CTA；
- 不自行判断“今天应该主推哪个产品”；
- 不把某个天象窗口、价格或产品状态擅自当成当天商业任务。

只有 Suen 当天明确指令，或当天总控已经明确分配商业方向时，专用栏目才可以承载相应商业信号。

这个兜底的目的，是防止多个平台在拿不到总控时各自同时销售。

## 5. 独立项目边界

`上海省钱情报局` 等明确独立商业项目，不纳入本神秘学内容商业总控的：

- 有效询盘；
- 成交；
- 商业信号；
- 产品优先级；
- 神秘学内容调度。

不得把星符、仪式、塔罗、原典研究、Suen Akhet 数据库或本项目 30 天商业目标塞进上海省钱情报局内容。

独立项目的真实任务状态与自动化状态回到对应专用项目 / 自动化系统读取。

## 6. 版本冲突

运营规则冲突时默认：

Suen 最新明确指令 → 最新 Slack 当日正式经营决定 / 状态 → GitHub 当前正式运营规则 → 历史记录。

注意：Slack 的历史旧消息不能覆盖 GitHub 当前正式长期规则；只有当前仍有效的当日经营决定 / 状态才能高于静态规则。

知识资产内部规则不由本仓库裁决，回到对应专用真源处理。

## 7. 核心边界

**Slack = 今天发生什么**  
**GitHub = Slack / ChatGPT 怎么工作**  
**Obsidian / Library / Drive = 知识资产本身是什么**  
**专用择时系统 = 技术判断怎么做**
