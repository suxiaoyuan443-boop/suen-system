# Suen｜每日总结与更新工作流

状态：当前正式规则  
最后核对：2026-09-19

本文件只保留日常运行流程。平台细节、商业指标、实验和文笔不在这里重复。

## 一、总流程

`总结 → 补齐事实台账 → 更新 → 读取动态状态 → 判断瓶颈 → P0/P1/P2 → 专用对话执行 → 发布 → 后续复盘`

## 二、Suen 说“总结”

目标：补齐已经发生的事实，不定新题。

步骤：

1. 读取 Slack `#内容历史台账`；
2. 确认哪些内容真的已经发布；
3. 告诉 Suen 当前缺哪些必要数据；
4. 未知数据不估算；
5. 补齐后按 `内容复盘台账模板.md` 记录。

必须区分：

- 内容实际发布日期；
- 本次复盘日期；
- 内容涉及的仪式 / 星符执行日期。

计划发布、成品完成、准备发布都不等于“已经发布”。

询盘 / 成交只有能可靠确认来源时才归因给具体内容。

## 三、Suen 说“更新”

先重新读取 Slack：

1. `#内容历史台账`
2. `#商业决策总控`
3. `#天象检索与预约`

然后：

1. 判断当前一个主要瓶颈；
2. 检查当前可售 / 可预约状态；
3. 检查 `#商业决策总控` 中是否存在当前有效的待发内容池 / 冷却区；
4. 先从待发内容池里选当天最合适的生产单元；池内没有合适候选、数量不足或最新数据已经改变判断时，再补新候选；
5. 决定 P0 / P1 / P2；
6. 如需新前台题，再读取内容地图、对标和硬门槛；
7. 如需商业动作，再读取商业信号规则；
8. 如需实验 / 重发判断，再读取内容实验规则；
9. 写当天短总控；
10. 只给真正需要执行的专用对话短交接。

## 四、待发内容池与冷却区

待发内容池属于 **Slack 动态经营状态**，默认保存在 `#商业决策总控`，不把每天的候选题复制进 GitHub。

日常执行：

- 每次“更新”先看当前有效池，不从零开始想题；
- 候选题只代表“值得继续推进”，不等于当天最终定题；
- 最终定题仍要结合最新第一方数据、最近 7 天跨账号重复、证据可答性、实际工作量和当前主任务；
- 抖音大号候选池原则上保持约 3—5 个可推进题；
- 抖音小号保持约 2—3 个真实素材方向；
- 小红书保持至少 2 个可发备选；
- 已发布、淘汰、进入冷却或因证据不足暂停的候选要及时替换，不让池子变成历史垃圾桶；
- 冷却区用于提醒近期不要机械重复同一观看体验；换账号、换栏目或只改标题，不自动视为新题；
- 如果池内候选已经完成过部分资料可行性确认，正式生产时沿用已确认结果，但仍需补齐当前栏目要求的完整证据与素材，不重复从零做无必要研究。

GitHub 只保存这套**维护机制**；具体候选题、优先级、冷却项与当日状态继续以 Slack 最新记录为准。

## 五、Slack 读取失败

### 台账读不到

不能声称已经完成最新内容表现诊断。

### 商业决策总控读不到

不能假设最新询盘、报价、成交和当天商业决定；不新增销售动作。

### 天象频道读不到

不新增星符 / 仪式日期宣传，不猜窗口状态。

如果用户要求继续，只能明确按当前可确认信息做临时判断。

## 六、动态状态有效期

以下信息使用前必须确认今天仍有效：

- 价格
- 可售 / 可预约状态
- 排期 / 容量
- 折扣 / 套餐
- 天象宣传资格
- 今日主推 / 今日纯内容 / 今日明确不推

昨天的“今日决定”跨日自动失效。

带明确测试周期的规则到期后也不能自动续期。

## 七、定题只在需要时加载重规则

如果今天只是执行已定任务，不机械读取对标、100 分模型和所有栏目规则。

只有要定新的前台题时，才加载：

- `内容地图.md`
- `内容商业对标系统.md`
- `选题定稿硬门槛.md`
- 对应平台 / 栏目当前规则

先看 Suen 自己的真实第一方信号，再看外部 benchmark。

## 八、生产保护

题目、主任务、商业边界确定后进入生产保护。

普通文笔、配图、链接、排版、素材匹配等问题由执行对话自行解决，不因此重新推翻选题。

P0 未完成前，不用 README 美化、仓库整理等非阻塞维护抢时间。

## 九、Patreon

Patreon 不机械进入每天任务。

以下情况才在“更新”里显示：

- 本月约 4 篇内部节奏明显需要推进；
- 当前处于冷启动建库；
- 已有成熟研究 / 实践记录，今天完成边际成本低；
- 出现真实订阅、取消或付费来源需要处理。

## 十、复盘

发布后取得合理数据窗口，再回看发布前已经确定的主任务 / 假设。

不要看完结果后倒推“这条本来就是在验证什么”。

详细结果判定读取：`内容实验与验证规则.md`。
