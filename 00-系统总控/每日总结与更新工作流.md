# Suen｜每日总结与更新工作流

状态：当前正式规则
最后核对：2026-09-19

本文件规定每天实际怎么运行：

**总结 → Suen 补齐内容台账 → 更新 → 读取最新经营状态 → 诊断 → 账号结构检查 → 第一方历史信号 → 动态对标 / 定题 → 主要验证假设 → P0 / P1 / P2 排序 → 短交接 → 生产保护 → 发布闭环 → 后续复盘验证。**

周级商业复盘单独读取：`每周商业复盘.md`。

任务优先级与生产保护读取：`总控简化与生产保护规则.md`。

商业信号与动态状态读取：`商业信号与动态状态规则.md`。

第一方信号、外部 benchmark 与跨账号迁移规则读取：`内容商业对标系统.md`。

制作耗时与投入产出读取：`生产投入产出规则.md`。

主要验证假设、结果判定与信号升级读取：`内容实验与验证规则.md`。

发布时间与时段测试读取：`平台发布时间与时段实验规则.md`。

## 一、Suen 说“总结”时

“总结”阶段只处理已经发生的内容数据，不做当天新选题。

这里的“总结”是商业总控 / 内容台账触发词；销售私聊只有明确说“生成总结”才生成客户商业记录。

实际格式读取：`99-模板/内容复盘台账模板.md`。

### 固定步骤

1. 读取 Slack `#内容历史台账`，确认已经记录到哪里；
2. 确认哪些内容**实际已经发布**；
3. 根据当前台账告诉 Suen 今天缺哪些平台 / 字段；
4. 未知数据不估算；
5. Suen 查看各平台后台，把真实数据直接补进 `#内容历史台账`；
6. ChatGPT 默认不代替 Suen 抄后台数据，除非当次明确要求代发；
7. 抖音大号、抖音小号、小红书、公众号、朋友圈分别记录；Patreon 当天有新帖或需要补会员 / 收入事实时也单独记录；
8. 公众号贴图与长文分别记录；Patreon 公开帖与付费帖区分记录；
9. 抖音小号已发布时，尽量补齐后台分析所需的 `内容类型 / 内容形式 / 入口结构 / 主题标签`；判断不稳时写“待确认”，不要求 Suen 为了分类额外做复杂工作；
10. 方便时只在内容第一次进入台账时补一个真实 `制作耗时档位`；不知道就不填，不追问旧内容；
11. 如果对应内容发布前已经在 `#商业决策总控` 写过主要验证假设，并且当前数据窗口已经足以初步判断，则由总控自行回看假设，写 `支持 / 不支持 / 无法判断`；不要求 Suen 额外填写实验表。

最省事闭环：

**ChatGPT 检查缺项 → Suen 直接在 Slack 填 → 填完说“更新”。**

### 计划 ≠ 已发布

`计划今天发 / 成品做好了 / 准备发布` 都不等于实际发布。

只能确认计划时：

- 标记“发布状态待确认”；
- 不把计划日期当实际发布时间；
- 不为了补齐台账猜测已发布。

### 三类日期分开

- 内容实际发布日期；
- 复盘日期；
- 内容中提到的仪式 / 星符执行日期。

仪式日期不能代替内容发布时间。

### 询盘 / 成交归因

只有能可靠确认由当前内容带来时，才把私信、有效询盘、成交写进该内容复盘。

只能确认平台、不能确认具体内容时：

- 只归因到平台；
- 不因为“当天刚发了这条”就强行归因。

有效询盘、成交、成交金额、预计毛利 / 净利润统一执行 `商业指标口径.md`。

### 评论信号

有实际判断价值时单列，例如：

- 为什么喜欢；
- 哪里看不懂；
- 想继续看什么；
- 如何理解 Suen 定位；
- 有没有现实需求；
- 有没有服务认知；
- 有没有潜在商业需求；
- 是否出现圈内 / 深度兴趣受众识别。

普通夸赞、表情、闲聊只计评论数量即可。

### 主要验证结果怎么回看

只回看**发布前已经写好的假设**。

根据 `内容实验与验证规则.md`：

- 主要观察指标与假设方向一致 → `支持`；
- 没有出现预期方向或明显相反 → `不支持`；
- 数据太少、多变量同时变化、平台异常或关键指标缺失 → `无法判断`。

第一次支持仍然只算单样本信号。

不能看见其它指标漂亮以后，临时换一个实验目标宣布成功。

## 二、Suen 说“更新”时，先刷新当天真实状态

“更新”阶段必须重新读取最新 Slack：

1. `#内容历史台账`
2. `#商业决策总控`
3. `#天象检索与预约`

不用上一轮记忆代替实时读取。

如果是新会话第一次进入总控、仓库刚修改、规则有冲突或 Suen 明确要求按最新仓库执行，同时刷新 GitHub 最小启动读取集。

### Slack 读取失败协议

先根据 `07-销售与Slack/Slack架构.md` 的 Channel ID 重试。

仍失败时：

- `#内容历史台账` 失败 → 不能声称完成基于最新 3—7 天数据的确定性瓶颈诊断，也不能声称已经检查完整第一方历史信号；
- `#商业决策总控` 失败 → 不假设最新询盘 / 报价 / 成交，也不能可靠读取上一轮主要验证假设；不新增销售动作；
- `#天象检索与预约` 失败 → 不新增星符 / 仪式宣传，不猜预约状态或日期。

如果 Suen 要求立即继续，只能基于当前已知真实数据做**临时判断**，并明确覆盖不完整。

Slack 写入失败时，可以显示应写内容，但必须明确“未成功写入”，不能声称已经保存。

## 三、先检查日期与动态状态是否仍有效

在使用任何阶段性数字前检查：

- 当前 30 天目标是否仍在周期内；
- 公众号阶段测试是否已到复核点；
- 其它阶段规则是否已经过期。

过期但没有新版本时：

- 旧数据只作为上一阶段参考；
- 不自动续期；
- 不擅自按比例重算新 KPI。

### 当日经营决定跨日失效

`今日纯内容 / 今日主推 / 今日明确不推 / 今日唯一商业信号 / 今日停更` 默认只对 Asia/Shanghai 当天有效。

跨日以后重新读取当天 Slack，不拿昨天的决定直接继续执行。

### 动态产品状态

公开使用这些信息前确认今天仍有效：

- 当前是否可售 / 可预约；
- 价格；
- 排期 / 容量；
- 交付方式；
- 折扣 / 套餐；
- 付款 / 退款条件；
- 天象宣传资格。

不能从旧朋友圈、旧视频、旧报价或历史聊天自动沿用。

---

### Patreon 月度节奏

Patreon 不机械日更，但总控不能因为它不属于每日 P0 就长期忘记。

每次周复盘必须检查；日常“更新”只有在以下情况才需要把 Patreon 显示到今日任务：

- 本月付费内容进度明显落后于“平均约 4 篇”的内部节奏；
- 已有成熟研究 / 实践记录，今天追加一篇的边际成本较低；
- 当前正在做 Patreon 冷启动内容库；
- 已出现真实订阅 / 取消 / 付费来源，需要经营处理。

如果当天无需介入，不必为了模板完整每天显示 Patreon。

## 四、判断当天一个主要瓶颈

结合最近 3—7 天真实表现和更长历史基线，判断主要问题：

- 流量；
- 精准涨粉；
- 服务认知；
- 询盘；
- 成交。

同时看：

- 播放 / 阅读 / 曝光；
- 留存 / 平均观看 / 完播等平台可见指标；
- 点赞、收藏、评论、分享；
- 涨粉、主页访问；
- 私信、有效询盘、报价、成交；
- 评论信号；
- 最近内容体验是否重复；
- 当前产品状态；
- Suen 当天工作量；
- 已有真实制作耗时与返工负担。

不拿单条爆款当账号正常基线。

商业数字需要累计时先执行 `商业指标口径.md`。

## 五、定题前先检查账号当前内容结构

这一步与“最近 7 天重复度”分开执行。

对需要当天定新前台题的平台，先看：

- 当前账号已经实际发布了哪些栏目 / 内容类型；
- 主页给陌生人的第一印象是什么；
- 是否已经由某一个栏目、文化或观看体验占据绝大多数；
- 如果账号仍处于早期、实际样本很少，当前全部已发布内容共同定义了什么账号认知。

### 抖音大号额外要求

如果大号当前实际发布样本很少：

- 优先查看**当前全部已发布内容**，不能只看近 3—7 天；
- 如果少量已发布内容几乎全是同一个栏目，下一条继续同栏目时必须有明确理由；
- 当两个候选题质量、证据、流量潜力接近时，优先补全主页内容结构，让观众看到第二种 / 第三种真实内容能力；
- 如果当前主页已经被一种观看体验明显占据，最终定题前执行 `选题定稿硬门槛.md` 的跨内容体验候选比较。

这不是机械栏目轮播。

如果某个同栏目候选明显更强、具有时效、数据优势、证据优势或真实商业价值，可以继续发；但需要先做过账号结构比较，而不是因为“这个题不错”就忽略主页已有内容。

如果 Slack 对早期内容记录不全，而 Suen 明确补充了真实已发布内容，以 Suen 最新明确事实为准。

## 六、先看 Suen 自己的第一方历史信号

在查看外部 benchmark 以前，先读取当前可取得的第一方样本。

至少看：

- 抖音大号历史栏目 / 题目 / 数据；
- 抖音小号的 `内容类型 × 入口结构 × 内容形式`；
- 小红书已经验证过的题目结构、收藏、涨粉与主页访问；
- 公众号贴图 / 长文已经出现的入口与搜索信号；
- 能确认来源的询盘 / 成交内容归因；
- 有判断价值的评论信号；
- 已知制作耗时档位。

### 第一方信号强度

统一执行 `内容商业对标系统.md`：

- **单样本信号**：说明这个组合值得继续验证，不写成永久公式；
- **重复信号**：多个相对可比较样本反复出现同一方向；
- **稳定结构**：多个时期 / 多个可比较样本，或跨平台迁移后在相同目标指标上重复有效。

### 先看“哪个结果”，再说“表现好”

不得用一个指标代表所有目标。

例如：

- 点赞高但涨粉弱 → 更可能是互动 / 氛围价值，不自动判为 B｜精准涨粉强；
- 播放高但收藏 / 主页访问弱 → 可能是宽流量，不自动判为品牌结构；
- 收藏 / 涨粉不错但播放一般 → 可能更适合精准受众，不因为绝对播放低就淘汰；
- 客订 / 反馈内容能建立服务认知，但不自动说明它适合公域拉新。

### 跨账号迁移

小号跑出的好结构，只作为大号的**入口假设 / 选题假设**。

大号仍需重新检查栏目路由、主页结构、证据、素材与当天任务；不能把小号跑通直接写成“大号已验证”。

## 七、需要新前台题时，再刷新当天对标动态样本

完整规则读取：`内容商业对标系统.md`。

对标分两层：

### A｜长期方法

五个 benchmark 的长期稳定方法一直参与判断，不需要每天重新刷五个主页。

### B｜近期真实创作

每个 Asia/Shanghai 运营日第一次需要确定新的前台题目时：

1. 根据当天瓶颈与 A / B / C / D 主任务；
2. 选最相关的 **2—3 个对标账号**；
3. 实际查看近期真实创作，默认优先最近约 7—30 天；
4. 提取入口、标题、开头、结构、资料组织、系列形式、商业信息位置等方法；
5. 不直接复制题目。

同一运营日已经刷新且任务没有变化，可以复用，不重复搜索。

近期样本无法可靠取得时：

- 标记“近期样本未可靠取得”；
- 不把长期印象冒充刚看过近期内容；
- 可以换另一个相关 benchmark；
- 对近期趋势判断降级，不编造。

近期动态样本不固化进 GitHub；GitHub 只保存采样方法。

## 八、前台选题通过硬门槛以后再进入生产

执行：`选题定稿硬门槛.md`。

至少检查：

- 当前瓶颈；
- **第一方历史信号及其强度；**
- **账号已有内容 / 主页结构；**
- 栏目路由；
- 五个长期 benchmark 方法；
- 当日相关近期样本；
- Suen 100 分模型；
- 最近 7 天重复度；
- 核心答案证据可答；
- 真实素材可取得；
- 商业边界；
- 历史制作成本 / 当天工作量；
- P0 工作量可行。

未通过：

`候选题｜待筛选`

不得生成正式执行令。

通过后默认只对 Suen 显示：

`选题状态：已通过硬门槛`

正常稳定日不把五个 benchmark 明细、100 分细项、SHA 清单全部展开。

### 通过硬门槛后，发布前写 1 个主要验证假设

执行：`内容实验与验证规则.md`。

新的正式前台内容原则上记录：

```text
主要验证：
主任务：A / B / C / D
主要观察指标：
对照基线：最近最可比样本 / 无可靠可比样本
```

规则：

- 必须在结果出现以前写；
- 只设 1 个主要变量或组合假设；
- 与 A / B / C / D 主任务绑定；
- 不为了实验增加制作复杂度；
- 时效通知、已确认商业动作或稳定结构复用可以写“无新增实验”。

主要验证假设保存在当天 `#商业决策总控`，不写进 GitHub 动态规则。

## 九、再排 P0 / P1 / P2

### P0｜今天必须先完成

当天最重要的生产单元。

当前通常优先：

**抖音大号 1 条 + 小红书同步同一支完整成片。**

总控必须先保证 P0 方向、题目、商业边界和执行令清楚。

### P1｜P0 完成后值得做

当天有明确价值且工作量允许：

- 公众号贴图；
- 有强题时的公众号长文；
- 当天确有必要的朋友圈；
- **已有真实素材或低成本可完成，并且能验证一个明确第一方内容假设的抖音小号轻量测试。**

小号进入 P1 的前提是：不发展成新的重研究项目，不影响 P0，不为了凑更新而做。

P1 如果以“轻量验证”身份进入，同样只设 1 个主要验证假设。

### P2｜有余力再做

- 抖音小号普通更新；
- 非紧急系统维护；
- 不影响当天经营结果的附加任务。

P2 不得挤占 P0。

如果当天出现更高优先级的真实商业 / 平台事件，可以调整 P0，但必须说明理由。

## 十、各平台当天判断

如果当天有实际发布任务，总控同时给出建议发布时间，并标明属于历史基线 / 挑战点 / 临时测试 / 已有稳定窗口。发布时间不作为内容质量替代品，完整执行 `平台发布时间与时段实验规则.md`。


### 抖音大号

当前基线：每天 1 条，只发 7 个前台合集中的 1 个。

总控决定：栏目、题目、A/B/C/D、商业边界。

例外停更必须写清真实原因。

### 小红书

当前基线：每天 1 篇 / 1 条。

通常优先同步当天大号同一支成片。

同步时只算**一个制作任务**；在同一个抖音栏目专用对话里补小红书标题、封面文字和发布配文，不重做第二支视频。

商业 CTA 如果已经在视频里，发布到两个平台会形成两个真实平台商业触点；商业密度按实际平台计算。

同一成片如果用于验证内容结构，抖音和小红书的结果分别看，不把两边数据简单相加当成一个实验结果。

《长卷》不机械日更。

### 公众号

贴图与长文分别判断：

- 贴图：推荐 / 陌生入口价值；
- 长文：深度题材是否值得当天投入。

不恢复机械“每天 1 长 + 1 贴”。

同日两篇最多一篇出现轻商业信息，并服从当天主要商业信号。

### 朋友圈

只有真实工作记录、客户反馈、产品过程、已确认窗口或明确商业承接需要时安排。

不为日更硬发，不重复催同一个窗口。

### 抖音小号

不机械日更。

它承担的是 **Suen 的实践人格层 + 第一方内容试验场**：真实实践、供奉、器物、观点、互动和直接问题型机制解释都可以出现。

当天是否发，优先判断：

- 有没有现成真实素材 / 工作过程；
- 有没有值得继续验证的入口结构；
- 有没有评论区 / 实践现场自然产生的问题；
- 能不能用较低制作成本完成；
- 会不会挤占大号 P0；
- 会不会和当天商业信号冲突。

### 独立项目

上海省钱情报局等独立项目不进入本神秘学商业总控的内容、询盘、成交、商业信号统计。

## 十一、统一商业密度

长期约：

- 正常内容 80%；
- 明显商业信号 20%。

原则上：

- 一天最好 1 个主要商业信号；
- 确有真实需要时最多 2 个明显商业触点；
- 同一个产品跨平台重复卖，仍按多个实际触点计算。

总控最终必须明确：

- 【今日主要商业信号】
- 【今日明确不推】

纯内容日不自行增加报价、预约、购买、私信 CTA。

具体时分冲突时，总控不自行挑一个时间公开。

## 十三、写入 Slack 时保持短

不重复粘贴所有播放点赞明细，不把完整内部评分表写进 Slack。

如果没有新增实验，`主要验证：无新增实验｜执行已验证稳定结构` 即可。

## 十四、专用对话只收到短执行令

使用：`99-模板/专用对话执行提示词模板.md`。

主要验证假设通常留在总控，不要求专用对话为了实验额外改造制作流程；只有它与“今日重点”直接相关时才传。

专用对话自己读取当前 GitHub 真源。

## 十五、进入生产以后执行“生产保护”

题目已经通过硬门槛，并确定：

- 栏目 / 内容产品；
- 题目；
- 核心问题；
- A / B / C / D 主任务；
- 商业边界；
- 主要验证假设 / 无新增实验。

则进入生产保护状态。

### 可以打断生产的真实阻塞

- 核心事实 / 证据可能错误；
- 核心问题实际答不出来；
- 栏目路由错误；
- 商业 / 天象 / 法律 / 平台硬边界冲突；
- Suen 新补充的真实账号内容结构使原选题判断失效；
- Suen 明确改变任务。

### 不应打断 P0 的问题

- 普通文笔问题；
- 图片匹配 / 裁图 / 链接问题；
- 排版问题；
- README 可以更漂亮；
- 模板还有轻微重复；
- 仓库文件名可以更统一；
- 非必要的新系统想法；
- 为了“实验更纯”想临时增加拍摄、重新设计大量素材或继续拆更多变量。

这些优先由执行对话自行修；非阻塞性长期维护等 P0 完成后再处理。

**先完成当天成品，再修不阻塞发布的系统问题。**

## 十六、发布闭环

系统目标是让当天 P0 真正变成**可发布成品**，但不能把“成品已完成”自动写成“已经发布”。

区分：

- `生产完成`：最终成品已经达到可录制 / 可剪 / 可发布状态；
- `实际发布`：Suen 已真实发布，或有可靠外部证据确认发布。

没有实际发布确认时：

- 不写入内容历史台账为“已发布”；
- 不猜发布时间；
- 不开始正式验证结果判断；
- 可以保留“成品完成 / 待发布”作为当前对话状态，但正式复盘等真实发布后再做。

如果 P0 因真实阻塞没完成：

- 直接写具体阻塞；
- 给当前最佳替代方案；
- 不用一整天非阻塞性系统维护掩盖“今天没有成品”这个事实。

## 十七、对 Suen 的默认最终输出

正常稳定日只回答：

- 今天卡在哪里；
- P0 是什么；
- P1 是否值得做；
- 有实际判断价值时，用 1 句话告诉 Suen 这条主要在验证什么；
- 今天卖不卖；
- 今日明确不推；
- 需要复制到哪个专用对话的短执行令。

不要写成长篇运营报告。

内部检查保持严格；对 Suen 的操作界面保持简单。
