# Suen｜专用对话执行提示词模板

状态：当前正式模板
最后核对：2026-09-17

用于商业总控完成当天判断以后，把任务交给具体栏目 / 平台专用对话。

核心原则：

**总控只传递“今天为什么做、做什么、承担什么任务、哪些边界不能碰”；专用对话继续负责按自己的长期规则生成完整成品。**

不要在总控里重新复制整套栏目长期规则，也不要因为流量优化替栏目改掉 Suen 文笔。

## 前台栏目名 ≠ ChatGPT 对话名

GitHub 记录的是当前正式前台结构和执行规则，不保证用户的 ChatGPT 专用对话标题已经同步改名。

例如：

- `隐理 / 世问` 是当前前台合集名；
- `口述` 只保留为内部内容母类；
- 旧专用对话如果仍保留历史标题，不代表前台继续使用旧合集名。

因此总控交接时：

- 必须明确写清**今天前台发布属于哪个合集**；
- 如果已知用户现有专用对话映射，可以告诉用户去哪个对话执行；
- 如果不知道某个新合集是否已经有独立专用对话，**不要虚构一个对话名 / 对话 ID**；
- 可以直接给标注好“平台 / 前台合集”的提示词，由 Suen 放入实际使用的专用对话；
- 专用对话读取 GitHub 当前栏目规则后再执行，避免旧对话名称把内容重新拉回旧栏目结构。

## 规则真源与读取验收

GitHub 当前正式规则不是“建议参考”，而是专用对话生成正式成品前的配置真源。

完整读取验收统一执行：

`00-系统总控/规则读取验收协议.md`

正式成稿交付前统一执行：

`00-系统总控/文笔成稿验收协议.md`

如果当前专用对话可以访问 GitHub：

- **必须实际调用 GitHub 连接器读取**该平台 / 栏目在 `suen-system` 中的当前正式规则；
- 同时读取 `00-系统总控/Suen统一文笔总则.md`；
- 同时读取 `00-系统总控/文笔成稿验收协议.md`；
- 如果是视频任务，再读取 `99-模板/视频类统一交付格式.md`；
- 总控提示词另外列出的文件也必须实际读取；
- 不能用旧对话记忆、项目摘要或“之前读过”代替本轮必要读取；
- 读取完成后先做规则冲突检查，再开始正式生成。

当 Suen 明确要求“先读仓库 / 按最新 GitHub 执行”，或当天已经出现过规则读取错误 / 冲突时：

- 正式成品前必须先输出简短【GitHub读取回执】；
- 回执至少写清：实际读取文件路径、当前 SHA、直接影响本次成稿的硬规则、是否存在冲突；
- 没有实际读取成功时，禁止写“已读取 / 已按最新仓库执行”。

如果当前专用对话无法可靠读取 GitHub：

- 明确写：`当前对话无法实际访问 GitHub，因此不能声称已读取仓库。`；
- 使用本对话中最新、最明确的长期规则 + 当天总控交接；
- 遇到明显冲突时以 Suen 当天最新明确指令为准；
- 商业方向无法确认时默认纯内容，不自行加销售 CTA。

如果 GitHub 连接器本来可用，但关键文件读取失败：

- 不得继续生成正式最终成品；
- 先说明失败文件并重试 / 修复；
- 读取成功后再继续。

## 通用模板

```text
执行今天的正式更新。

【GitHub读取是强制前置步骤】
如果当前对话可以访问 GitHub，必须先实际调用 GitHub 连接器读取：
1. suen-system 中本平台 / 本栏目的当前正式规则；
2. `00-系统总控/Suen统一文笔总则.md`；
3. `00-系统总控/文笔成稿验收协议.md`；
4. 本任务对应的统一交付规则；
5. 如果今天是视频任务：`99-模板/视频类统一交付格式.md`；
6. 本提示词另外点名的其它规则文件。

同时执行：
`00-系统总控/规则读取验收协议.md`

禁止用旧对话记忆、项目摘要、之前读过或本提示词对规则的概括，代替本轮实际读取。

读取完成以后，先输出：

【GitHub读取回执】
已实际读取：
- 文件路径｜SHA
- 文件路径｜SHA

本次直接影响成稿的硬规则：
1.
2.
3.
4.
5.

冲突检查：无 / 有

如果无法实际访问 GitHub：
明确写“当前对话无法实际访问 GitHub，因此不能声称已读取仓库”，再使用本专用对话内最新长期规则 + 以下今日总控任务。

如果 GitHub 可访问但关键文件读取失败：
停止生成正式成品，明确失败文件；不得声称已读取，也不得继续输出最终版。

【今日总控任务】
平台：
前台合集 / 内容产品：
题目 / 选题方向：
主任务：A｜流量 / B｜精准涨粉 / C｜服务认知 / D｜商业承接
辅助目标：（如专业信任、收藏、搜索、评论互动等；没有则省略）

【为什么今天做这个】
用1—3条写清当前瓶颈和这条内容要解决什么。

【今天需要特别优化】
- 第一屏 / 前2—5秒：
- 时长：
- 信息顺序：
- 案例数量：
- 素材重点：

【文笔】
继续严格执行本栏目当前正式文笔规则 + `00-系统总控/Suen统一文笔总则.md`。
运营优化只调整入口、时长、顺序、案例和画面，不改成普通营销号 / AI短视频文风。

正式成稿发出前，必须执行 `00-系统总控/文笔成稿验收协议.md`，至少自行检查：
- 有没有同义复述；
- 有没有连续否定 / 连续反驳；
- 有没有用抽象词替代具体对象和动作；
- 有没有为了显得“深”擅自拔高理论；
- 有没有一段删掉后信息完全不损失；
- 口播是否真的能自然说出来。

发现问题先自行修改，不把明显的 AI 文风、重复和抽象化问题交给 Suen 再发现。

【商业边界】
今天：纯内容 / 允许的唯一商业方向

如果纯内容：
禁止自行加入接单、报价、预约、购买、私信引导或其它商业CTA。

如果允许商业信息：
只能使用总控明确指定的商业方向，不得自行扩展成第二个产品 / 服务广告，也不得顺手再推其它预约、课程、数据库或实物。

【交付】
规则读取与冲突检查通过后，再按本栏目当前正式交付格式生成最终可执行成品。
正式交付前必须完成文笔成稿验收；未通过不得标记为“最终版 / 可录制版 / 可发布版”。
如果是视频，必须使用统一双栏格式：左边完整口播 / 台词，右边对应图片 / 素材链接与画面说明；不要把口播和素材拆成两个独立部分。
不要先写长篇修改思路。
```

### A / B / C / D 说明

- `A｜流量`：陌生人点击、停留和进入。
- `B｜精准涨粉`：让真正相关的长期受众识别并关注 Suen。
- `C｜服务认知`：让观众理解 Suen 会判断 / 处理什么以及工作边界。
- `D｜商业承接`：在总控明确允许的前提下，把既有需求承接到询盘、报价、预约、购买或成交。

同一条内容只指定一个主任务；专业信任、收藏、搜索等可以作为辅助目标，不再和 A/B/C/D 并列成第五种主任务。

完整定义见 `00-系统总控/商业总控.md`。

## 所有视频任务｜统一交付格式

只要当天任务是“需要制作视频成片”，总控交接必须默认带上：

```text
【视频交付格式】
执行 `99-模板/视频类统一交付格式.md`。

视频主体统一用两列表格：
| 完整口播 / 台词 | 对应图片 / 素材链接 |

左栏放一整段自然、连续、可直接录制的完整口播 / 台词；
右栏直接给这一整段真正对应的图片直链、来源页、已有素材或本人实拍镜头说明。

不要先给完整口播，再在后面另列一份素材清单。
不要机械一句一图。
如果是本人实拍，标明“本人实拍｜无外部链接”并写清怎么拍。
如果外部资料没有稳定图片直链，明确写“当前未取得稳定图片直链”，继续给来源页。
```

这一规则适用于：

- 抖音大号 7 个合集；
- 抖音小号；
- 同一成片同步到小红书的视频；
- 以后纳入本仓库的其它正式视频内容。

不适用于公众号、长卷、朋友圈等非视频产品。

## 抖音视频同步小红书时

如果当天小红书直接同步同一支抖音成片，在**同一个栏目专用对话提示词**末尾追加：

```text
【小红书同步】
今天小红书直接使用这支完整成片，不重新剪辑、不另做第二版视频。

在成片稿最后额外给：
1. 小红书标题候选
2. 封面文字候选
3. 小红书发布配文

只调整外围包装，不改变已经完成的视频主体。
商业边界与抖音当天总控一致。
```

不要再另外生成一个“小红书视频制作”提示词。

## 公众号

公众号提示词必须分别写清：

- 今天是贴图还是长文，或两者都有；
- 贴图承担推荐 / 陌生流量测试还是其它任务；
- 长文为什么值得投入深度工作量；
- 今天是否纯内容；
- 不得重新套用旧的“固定1长+1贴”逻辑。

如果只发贴图，就只要求贴图。

如果只发长文，就只要求长文。

如果当天贴图 + 长文都发布：

- **最多只有其中 1 篇允许出现轻商业信息；**
- 另一篇保持纯内容；
- 商业方向仍必须和当天总控指定方向一致；
- 不允许贴图卖一次、长文再卖一次。

公众号最终语言继续服从 `03-公众号/公众号文笔规则.md`，不能因为运营优化改成营销号腔。

---

## 朋友圈

只有总控明确安排朋友圈时才给提示词。

提示词必须继续服从：

- 像本人临时说话；
- 默认无标点；
- 不用运营文案腔；
- 天象只写可靠核查事实；
- 不虚构稀缺；
- 精确时分有冲突时不公开具体时间。

如果只是工作记录，不自动加销售CTA。

---

## 不执行的平台

当天明确“不发”的平台：

- 不生成成品；
- 不生成无用提示词；
- 不因为“顺便”增加第二份工作。

目标是让每天总控实际减少 Suen 的工作量，而不是把一个决策拆成更多任务。
